# re-conversation-state

Mapped the K1 GOG 1.03 (swkotor.exe, image base 0x400000) conversation, globals, journal, save/load, party and death/load-screen state from the Ghidra-readable corpus plus the kotorxid sqlite, with K2 counterparts from the K2 GOG-Aspyr name table (binary_id 22) and the K2 mac readable tree for struct offsets. Conversations live in a heap CSWSDialog (0x12c bytes) pointed to by the owner CSWSObject+0x34; the player's reply is consumed by CSWSDialog::HandleReply 0x5A03C0 via CSWSObject::ReplyDialog 0x4CB480(clientId, replyIndex, abortFlag, expectedEntryIndex, fromClient), which the GUI reaches through CGuiInGame::SetDialogSelection 0x62ADA0 + UpdateDialog 0x6339C0 and the network path reaches through CSWSMessage::HandlePlayerToServerDialogMessage 0x522810; replies are presented by CSWSDialog::SendDialogReplies 0x5A3820, which evaluates each link's Active script with CSWSDialog::CheckScript 0x59EC90 (VM RunScript + GetRunScriptReturnValue, int nonzero) and then calls CGuiInGame::HandleDialogReplies 0x634340. Skip/abort: CServerExoAppInternal::SkipPastDialog 0x4B1F90 sets CSWSObject+0x1F4=1 (honoured by IsDialogDelay 0x4CD2D0 only when dialog+0x3C Skippable), CGuiInGame::CloseDialog 0x6332B0 aborts, and VO wait is CSWSObject+0x38/+0x3C world-time delay plus wait_flags at +0x5C (bit1 camera, bit2 sound, bit4 anim, bit8 fade) set from SetDialogDelay 0x59FF50. Globals are a CSWGlobalVariableTable embedded at CServerExoAppInternal+0x100FC (getter CServerExoApp::GetGlobalVariableTable 0x4AEE60): 0x6EF open-hash GlobalIndentifier{char name[0x16]; u16 type_and_index} slots, type in bits 14-15 (0 bool bit-packed at +0xA668, 1 number bytes at +0xA6D9, 2 location 0x18-stride at +0xA8D0, 3 string CExoString at +0xB230), counts at +0xB258..+0xB264, so a full snapshot is a walk over the identifier array. The journal is a CExoArrayList<SJournalEntry 0x3C> at CSWPartyTable+0x11C (party table itself at CServerExoAppInternal+0x1B770, getter 0x4AEE70), tag at entry+0x18 and state at +0x20 (CSWSJournal::GetState 0x5C58A0 / SetState 0x5C5A40). Saves are directories 'SAVES:%06d - %s' (AUTOSAVE is slot 1, QUICKSAVE slot 0) containing savenfo.res (NFO GFF: AREANAME, LASTMODULE, TIMEPLAYED, SAVEGAMENAME, PCAUTOSAVE...), GLOBALVARS.res (GVT: Cat*/Val* lists), PARTYTABLE.res and SAVEGAME.sav (MOD V1.0 ERF of module .sav), and a load can be triggered from code without the menu by CClientExoApp::SendLoadGameRequest 0x5ED680(slot, dirName, lastModule) -> server MODULE minor 5 -> CServerExoAppInternal::LoadGame 0x4BA640, or directly by CServerExoApp::LoadGame (wrapper for 0x4BA640) after SetLoadFromSaveGame. Death/game-over is CClientExoAppInternal+0x2C0 game_over_state (GetGameOver 0x5EDC60, driven by TempDeathUpdate 0x4B6DA0 -> RunDeathSequence 0x5EDC40) and load-screen state is CClientExoAppInternal+0x288 area_not_ready_to_display plus CServerExoAppInternal+0x100B4 loading_module / +0x10080 move_to_module_pending; neither K1 nor K2 implements SetCutsceneMode, the cutscene analogue is the dialog AnimatedCut flag CGuiInGame+0xC0, the unpauseable counter CGuiInGame+0xD8 and input_disabled CClientExoAppInternal+0x2BC.

## Implications
- Reply pick = call CSWSObject::ReplyDialog(owner, clientId, linkIndex, 0, *(u32*)(dlg+0x70), 1) on the main thread (or write the MODULE/DIALOG minor-3 message); linkIndex is the position in entries[cur].link_entries, so the driver must enumerate that array (stride 0x18, +0x10 index, +0x14 display_inactive) and skip links whose Active script is false — evaluate with CSWSDialog::CheckScript(owner,&link.active) or read CGuiInGame+0x114/+0x118 (count/texts) plus CSWGuiDialog+0x1970[] (visible->link map) which the engine already computed.
- Dialog state oracle: conversation active iff CGuiInGame+0xB4 != 0 (K2: +0xCC); current node = CSWSDialog(+0x70 entry, +0x74 reply); strref = node+0x0C; waiting-for-player iff dialog+0x74 == -1 and CSWSObject+0x48 == 0 and CGuiInGame+0xD0 == 0; waiting-on-VO iff CSWSObject+0x5C != 0 or world time < CSWSObject+0x38/+0x3C.

- State snapshot = (a) walk CSWGlobalVariableTable at CServerExoAppInternal+0x100FC over 0x6EF GlobalIndentifier slots (K2: 0x93D) decoding type bits; (b) walk CSWSJournal at CSWPartyTable+0x11C (stride 0x3C, tag +0x18, state +0x20; K2 stride 0x38); (c) CSWPartyTable +0x00/+0x04.. for members, +0x30 availability, +0xEC leader; (d) module name at CSWSModule+0x5C via CServerExoApp::GetModule. ## Risks
- All K1 bodies are Ghidra decompilation marked NOT byte-verified; struct offsets in types.h passed size checks but field semantics (e.g. CSWSDialog+0x60/+0x6C, CGuiInGame+0xD4) are inferred from usage and could be misread.
- CSWSDialog is freed by StopDialog/ReplyDialog end paths (vtable slot 0 with flag 1); a driver reading dialog fields from another thread can race a free — read on the main thread (MainLoop detour) only.
- HandleReply is client/server merged: it calls CGuiInGame directly (HandleDialogReplyChosen, GetInGameGui) so it must run on the game thread with the client GUI initialised; calling it during load or from a worker thread will crash.
- Save loading from code without UnpackGame/SetLoadFromSaveGame(1) will load PARTYTABLE/GLOBALVARS but the module .sav files will not be in TEMP:, producing a fresh-module load (plot state mismatch) rather than an error.
- The kotorxid 'match' rows for K2 are noisy (several verified-wrong mappings); any K2 address taken from 'match' rather than from the binary-22 name table must be byte-checked before hooking.
- K2 Steam-Aspyr and K2 Linux have no usable names; the Steam +1-function shift claim comes from a json note whose expected_bytes were never regenerated.
- CSWGuiDialog::GetReplyIndex mapping (visible index -> link index via +0x1970[]) is inferred from SetReplies' store loop, not from a readable GetReplyIndex body.
- booleans[] size 0x71 bytes implies at most 904 boolean globals and numbers[] 0x1F4 implies 500; a mod that exceeds these would corrupt the walk, and the count fields at +0xB258.. must be used as bounds.
