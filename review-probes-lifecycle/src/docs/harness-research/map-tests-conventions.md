# tests-conventions

KotorPhasor builds with CMake+Ninja: native 32-bit Linux targets (libkphasor.so, kp_* offline tools) via g++ -m32 and a mingw cross-compile (kphasor.dll, binkw32.dll) that requires a prebuilt Windows third_party/luajit/src/libluajit.a (present, 2026-08-24). ctest -N lists 9 registered tests, all offline and self-process, but the current build/ is stale: kp_supporttest and kp_memtest executables are missing and the working tree has uncommitted edits to memory.cmake, hooks.cmake, registry.cpp and runtime.cpp. The repo defines exactly two test tiers in CMakeLists.txt:12-18: tools/ + ctest (offline, fast, CI-run) and scripts/harness/ (opt-in, needs a real KOTOR install, all bash, drives the game with Xvfb + xdotool typing into the cheat console and a pixel probe at (40,46)). Conventions are C++20 with -m32 -Wall -Wextra, no try/catch anywhere in src/, kp::platform::log(LogLevel,...) plus Runtime::log to <game>/kotorphasor.log, kConstant/trailing-underscore naming, includes rooted at src/, and a plain reasoned comment voice that uses " -- " or ":" instead of em dashes (commit 9c84883 removed em dashes; one remains at runtime.cpp:482). Lua scripts declare a global priority (higher runs first, ties by filename), define On* globals named from data/events.toml, abstain by returning nil, and are quarantined after error_budget=8. The "no Halo names" rule lives in both worktree AGENTS.md files and docs/api-dialects.md:5; another commit (3d84587) removed references to a named third-party fan project. contribute_findings.py writes hand-adjudicated bindings from data/adjudication/*_vm_bindings.json into the kotorxid.sqlite tables identity/logical_function/logical_name with method 'kotorphasor:adjudicated:v1' and tier 1, never overwrites, dry-runs by default, backs up first, and writes prose to <warehouse>/findings/kotorphasor-findings.md; it hardcodes game="K2". Python tooling is stdlib-only scripts under tools/ with no packaging; the python3 on PATH is linuxbrew 3.14.7 without PIL/numpy, while /usr/bin/python3 (also 3.14.7) has PIL, numpy, pytesseract, websockets, cv2 and pytest. Nothing in .cursor/.claude is versioned (.gitignore:38-39), and tmp/, build/, third_party/ and agentdecompile_projects/ are all ignored.

## Implications
- Place the Python driver under scripts/harness/ (e.g. scripts/harness/<pkg>/), not tools/: CMakeLists.txt:12-18 and CONTRIBUTING.md:85-102 define tools/ as the offline no-game tier that ctest runs and scripts/harness/ as the opt-in real-install tier; a driver that boots Wine belongs in the second. Keep any parts that need no game (log parsers, event-trace checkers, save-slot planners) under tools/ and register them in ctest.
- Do not add a Python dependency file that CI must satisfy: CI runs only cmake+ctest on ubuntu-latest with no pip step (.github/workflows/cmake-multi-platform.yml). Follow the existing tools/*.py shape: stdlib-first, `#!/usr/bin/env python3`, module docstring used as argparse help, sibling imports via sys.path.insert(ROOT/'tools'), dry-run by default with --apply / --check flags.
- If PIL/numpy/pytesseract/cv2/websockets are used for the periodic screenshot sanity check, the driver must run under /usr/bin/python3 explicitly (the PATH python3 is linuxbrew and lacks them), or degrade gracefully when imports fail. tesseract is at /usr/bin/tesseract.
- Register every offline check as a ctest via add_test inside the owning src/<module>/<module>.cmake fragment, guarded by `if(UNIX AND NOT WIN32)`, using either exit code (g_failures==0) or PASS_REGULAR_EXPRESSION + WORKING_DIRECTORY ${CMAKE_SOURCE_DIR}; declare OBJECT_DEPENDS on src/generated/*.inc; do not put anything needing Wine/Xvfb/a game into ctest.

Any harness run must start with a fresh `cmake --build build` and a passing `ctest --test-dir build --output-on-failure` before trusting the DLL/.so it deploys.
