# fill:Engine gates that can stall sc

Mapped the three CGuiInGame flags at +0xB4/+0xDC/+0xC04 (K1 GOG PC) and their K2 equivalents. The assignment's premise is wrong on one point: ExecuteCommandStartNewModule does not defer the move on +0xB4/+0xC04; it unconditionally calls SetMoveToModulePending(1) and only uses those flags to decide whether to StartGlobalFade(type 0). The only real MainLoop gate is CGuiInGame+0xDC == 0 (K2: +0xF4), the 'controller pause state' flag. +0xB4 is the global dialog state (SetGlobalDialogState at 0x62ec60), script-readable via GetIsConversationActive. +0xC04 is a transient 'ReturnToEbonHawk in progress' flag set and cleared synchronously around RunScript('k_sup_gohawk') in CSWGuiInGameMap::ReturnToEbonHawk and can never persist across a frame. +0xDC is set only when CExoInput::GetMainDeviceLost() != 0, and in every PC build in the corpus (K1 GOG 0x5df560 -> return_zero, verified byte-exact; K2 GOG-Aspyr -> CSWMGGunBank::IsTargetting = return 0; K2 mac -> CExoRawInputInternal::GetMainDeviceLost = return 0) that function is a stub returning 0, so the gate is dead on PC/Mac and cannot stall a headless run. Its only clearer is a GUI button (CSWGuiControllerLossBox::OnAccept), which would need input, but it is unreachable. Also verified the input-playback route: '-epf <file>' on the command line (checkCommandLineArgs 0x401700) -> CClientExoApp::setUpEventPlayBack 0x5ed830 -> CClientExoAppInternal::SetUpEventPlayBack 0x5f5910 -> loader 0x61fba0 parses a text file of '<ms> <K|C|I|Z|M|V|Y> ...' records into input_events; ProcessInput calls PlayBackInputEvents 0x6224e0 which dispatches K->HandleWMKeyDownMessage, C->HandleWMCharMessage 0x402240, I/Z->CClientExoAppInternal::HandleInputEvent 0x621210, bypassing DirectInput entirely and forcing a fixed 30 Hz snapshot rate. The genuine risk to script-driven transitions is not these flags but move_to_module_pending consumers (fade/pause state machine documented already in docs/event-semantics.md:456-462).

## Implications
- Do not treat +0xB4/+0xC04 (K2 +0xCC/+0xFFC) as transition gates. The only server gate on a pending StartNewModule is CGuiInGame+0xDC (K2 +0xF4) == 0, and on every PC/Mac build in the corpus that flag is provably unreachable (GetMainDeviceLost is a return-0 stub). A headless watchdog should therefore never attribute a stalled move_to_module_pending to these flags; if move_to_module_pending stays 1 across frames, look at MainLoop preconditions instead (reentrant_server_stats->continue_message_processing != 0, or MainLoop not being ticked).
- Oracle fields to expose per game: gui.dialog_active = CGuiInGame+0xB4 (K2 +0xCC) (same value GetIsConversationActive returns); gui.controller_pause = +0xDC (K2 +0xF4) as a cheap invariant that must always read 0 on PC (assert it; a nonzero value means the binary is not the corpus build); gui.return_to_hawk_running = +0xC04 (K2 +0xFFC), only ever nonzero inside a RunScript hook callback. server.move_to_module_pending/string are at CServerExoAppInternal+0x10080/+0x10084 in K2 mac and K2 gog-aspyr (K1 offset from types.h struct CServerExoAppInternal, 'doing_start_new_module' immediately precedes it).
- StartNewModule from a driver can be done by calling CServerExoApp::SetMoveToModulePending(1) + SetMoveToModuleString + SetMoveToModuleStartWaypoint directly from the main thread (exactly what the VM command does), skipping fade/movie side-effects; the move executes on the next server MainLoop tick. AddMoveToModuleMovie entries are the only client-side artefact of the VM path and can be omitted.
- The '-epf <file>' event-playback path (checkCommandLineArgs 0x401700 -> SetUpEventPlayBack 0x5f5910 -> PlayBackInputEvents 0x6224e0) is a supported, input-device-free route for feeding keys/chars/GUI input events: it bypasses CExoInput::GetEvents entirely, forces a fixed 30 Hz snapshot rate, and dispatches to HandleWMKeyDownMessage / HandleWMCharMessage(0x402240) / HandleInputEvent(0x621210). A harness can either write the text file format ('<ms> <K|C|I|Z> <arg(s)>') before launch or, in-process, AddTail its own records to CClientExoAppInternal::input_events and set capture_event_playback=1 at runtime to satisfy any GUI-driven gate (e.g. CSWGuiControllerLossBox::OnAccept, message boxes) without XTEST or pixel clicks. 'C' records reach DoConsole when the console is active, giving a second console-entry route besides the existing DoConsole hook.
- For K2, resolve the StartNewModule VM command by address/vtable slot (mac installs it at commands+0xfe8) because the gog-aspyr MANIFEST does not name it; the CGuiInGame offsets differ from K1 (dialog +0xCC, controller-pause +0xF4, return-to-hawk +0xFFC, saved-input-active +0x1000 mac / +0x1008 gog-aspyr).

## Risks
- All function bodies except return_zero are advisory-ghidra (not byte-verified); offsets were read from the decompiler's field names and from raw +0xNN accesses in K2, so a live memory read should confirm +0xB4/+0xDC/+0xC04 (K1) and +0xCC/+0xF4/+0xFFC (K2) before the harness relies on them.
- The native Linux 'kotor2' ELF is not in the readable corpus (only K2 mac, K2 win CD, K2 win gog-aspyr). Its GetMainDeviceLost is assumed to mirror the mac Aspyr build (return 0) but is unverified; if Aspyr wired SDL controller loss on Linux, +0xF4 could become reachable there.
- Even though +0xDC/+0xF4 cannot be set by the engine, a harness that pokes CGuiInGame memory or replays 'I' input events could set it indirectly (e.g. by invoking UpdateControllerPauseState after patching GetMainDeviceLost); if so the only clear path is EndControllerPauseState, which the harness must call itself.
- The real stall risk around module transitions is the pre-pending fade/pause state machine (nwsdoor.cpp:1946-1985 two-pass with SetPauseState(2) and a 500 ms re-post) and the client-side movie queue from AddMoveToModuleMovie, not the three flags examined; those were out of scope here and remain unmapped for a headless client.
- The '-epf' playback file is opened as 'HD0:<name>' through CExoFile TXT — the alias root and the exact first-line semantics (count vs rate) were not fully decoded; a malformed file silently leaves input_events empty and playback clears itself on the first frame.
