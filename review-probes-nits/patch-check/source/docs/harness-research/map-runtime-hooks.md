# runtime-hooks

KotorPhasor's runtime is a five-phase boot (identify → await_and_verify → resolve → install → boot_scripts) run on a worker thread started from DllMain (Windows) or an ELF constructor (K2 Linux, LD_PRELOAD), never on the loader lock. Hook bodies run synchronously on the game's own threads: main_loop_body (CServerExoAppInternal::MainLoop, K1 0x004BABB0 / K2-Linux 0x085CA53E) dispatches OnTick to every script's lua_State via lua_pcall, pumps kotor.registertimer timers, hot-reloads the script dir every 64 ticks, then calls the original 1..16 times per kp.speed; do_console_body (DoConsole, K1 0x00401F00, __cdecl per keystroke, unresolved on K2 Linux) buffers a line and either runs built-in `lua status|reload|exec`, dispatches OnConsoleCommand, or replays the characters to the engine. Every body arms KP_HOOK_GUARD (setjmp + thread-local FaultFrame) around its own work only; a claimed hardware fault writes two log lines, permanently poisons that site, and turns ALL Lua dispatch off (live=false) until `lua reload` is typed in the console. The runtime has zero socket/pipe/queue IPC: its only I/O is the per-line-appended kotorphasor.log, kotorphasor.ini, address/hookpack JSON, lua_situation.dat, and the hot-reload stat of <game>/kotorphasor/scripts/*.lua; the multiplayer example reaches the network through LuaJIT ffi → ws2_32.dll, not an engine socket library. Configuration is <game_dir>/kotorphasor.ini (script_dir, log_path, error_budget, hot_reload) plus exactly two env vars (KOTORPHASOR_HOOKPACK, KOTORPHASOR_ADDRESSES); kotorphasor.toml/KOTOR1_DIR/KOTOR2_DIR are tools-side only. OnScriptLoad fires from the worker thread before any game thread has entered a hook and before the VM bridge is captured (first RunScript), so kotor.* is unusable there; whether OnTick fires on the main menu is not established by the repo. An uncommitted hookpack/signature-resolve change is in flight touching registry.{cpp,hpp}, runtime.cpp (await_and_verify/resolve), api/memory.{cpp,hpp,cmake}, hooks.cmake, kp_hooktool.cpp; a harness is additive if it only appends to Runtime::install's `optional[]` table, adds an api module to the on_state_created lambda, and adds hook bodies/sites without reordering the boot phases. The existing harness (scripts/harness/*.sh) drives K1 only, via Xvfb+Wine+xdotool XTEST keystrokes gated on a pixel probe at (40,46), which is exactly the control strategy the new design must replace.

## Implications
- Put the control plane in C++ inside kphasor.dll/libkphasor.so as a new src/api module (e.g. src/api/harness.cpp with register_all) plus a listener that is pumped from main_loop_body: the only thread on which it is safe to call kotor.* routines, StartNewModule, timers, or touch lua_States is the one that calls CServerExoAppInternal::MainLoop (hook_bodies.cpp:252-290). A socket/pipe reader must therefore be non-blocking and drained inside the OnTick path (or a new guarded block in main_loop_body), never executed on the listener's own thread.
- Do not touch Runtime::resolve/await_and_verify/registry parsing (all in the in-flight diff). Additive integration points: (1) a new entry in the on_state_created lambda at runtime.cpp:473-489, (2) new rows in the `optional[]` table at runtime.cpp:385-402, (3) new bodies in hook_bodies.cpp, (4) new [[site]] rows in data/hooksites.toml and site objects in data/addresses/<build>.json, (5) new [[event]] rows in data/events.toml with regenerated src/generated/*.inc.
- Use the existing 'live' gate: a harness module must check kp::runtime::live() and active_host() exactly like the bodies do, and must arm KP_HOOK_GUARD_BEGIN(site, own_poison, fallback) around its own work so a harness bug poisons only the harness site.
- Because a claimed fault sets live=false globally and the only re-arm is the console's `lua reload` (unavailable on K2 Linux and on the main menu), the harness control plane needs its own re-arm/status command executed from C++ (call set_live(true) after Host::load_all) rather than relying on DoConsole.
- Add a heartbeat/state oracle the driver can read without the console: e.g. the harness module writes tick, module name (kotor.GetModuleName), phase, live flag, poisoned sites, last fault, and OnModuleLoad/OnModuleStart/OnModulePlayerEnter/OnAreaEnter timestamps to a file or socket every N ticks; today the only tick readout is `lua status` (hook_bodies.cpp:436).
- Hang detection = process alive AND heartbeat tick not advancing for T seconds; crash detection = process gone OR a '[fault] unrecoverable' / 'fault in hook body' log line; refusal detection = 'refusing to install:' line. The driver should tail kotorphasor.log (append-per-line, '[phase] msg' format) and pgrep -x swkotor.exe / swkotor2.exe / kotor2.
- Jumping to plot points should go through the routine bridge on the server thread (kotor.StartNewModule(module, waypoint) routine 509, kotor.SetGlobalNumber/SetGlobalBoolean, party/inventory routines), not the cheat console; the bridge is only bound after the engine's first RunScript (capture_vm), so the harness must wait for 'vm: routine bridge bound' before issuing engine calls, and must not issue them from OnScriptLoad (worker thread).
- A menu-free boot cave is required because DoConsole is dead on the main menu and unresolved on K2 Linux: candidates already in the tables are app.client_main_loop (kind must be changed to detour) and module.load_start; neither is hooked today, and neither has a Lua event contract yet.
- OnTick-on-main-menu is unproven; the first live experiment should log tick counts from boot (a trivial script) on k1_steam_103_unpacked to establish whether the server loop runs on the menu, during movies and while paused, since every timer, hot-reload and command-pump path in the design depends on MainLoop being called.
- kp.speed(N) only multiplies engine frames; Lua timers are ms-wall-clock (timers.cpp:279-294) and OnTick fires once per hooked frame, so a fast-forward mode must scale the timer clock via timers::set_clock or drive timers by tick, and the driver must not assume N× Lua ticks.
- Hot reload (host.cpp:384-420) already gives a zero-IPC command channel: dropping a new .lua into <game>/kotorphasor/scripts is picked up within 64 server frames and gets OnScriptLoad; a file-queue design can build on this without any new C++ but only while MainLoop is ticking and only at ~1 s latency.
- LuaJIT ffi + io/os are open in every script state (host.cpp:68; multiplayer example uses ws2_32 via ffi), so a pure-Lua UDP/TCP listener polled from OnTick is feasible on Windows/Wine; on native K2 Linux it would need libc via ffi instead of ws2_32.
- The driver must stage per-platform: K1 Wine via binkw32.dll proxy + kphasor.dll; K2 Linux via LD_PRELOAD=libkphasor.so on the kotor2 ELF (no proxy, no console); K2 Wine via the proxy. Config lives at <game_dir>/kotorphasor.ini and address tables at <game_dir>/kotorphasor/addresses/<build>.json or $KOTORPHASOR_ADDRESSES; the harness can point KOTORPHASOR_ADDRESSES/KOTORPHASOR_HOOKPACK at the checkout instead of copying.
- Screenshots for sanity only: X11 import on the Xvfb window as ui_wait.sh does; state should come from the in-process oracle, never from pixel (40,46).
- Keep harness scripts under the script error budget (8 errors per callback → quarantine, host.hpp:92-105): wrap OnTick work in pcall and report errors through the oracle rather than letting the host quarantine the control script.

## Risks
- Uncommitted hookpack/signature-resolve work touches registry.{cpp,hpp}, runtime.cpp resolve()/await_and_verify(), api/memory.{cpp,hpp,cmake}, hooks.cmake, kp_hooktool.cpp; any harness edit to those regions will conflict. Concurrent sessions share the main worktree (memory note), so re-check call sites before declaring done.
- OnScriptLoad runs on the worker thread concurrently with game startup; any harness code that opens sockets or calls engine routines there races the engine and the unbound VM (kotor.* bind latches permanently on first failure, runtime.cpp:635-640).
- A single fault in any hook body silently turns all Lua off (live=false) for the rest of the run unless `lua reload` is typed; a blind driver would see a hang-like silence, not an error, unless it watches for the 'fault in hook body' line.
- Faults inside engine code (e.g. a StartNewModule issued mid-frame from a bad state) are deliberately not claimed; under Wine that means a crash dialog/zombie rather than an exit code, so process-liveness checks must be paired with a heartbeat timeout.
- DoConsole is a per-keystroke handler that only runs while the engine's console is open; injecting engine cheat lines (warp, etc.) by calling the original DoConsole from C++ is untested and may require the console UI state, and the site is unresolved on K2 Linux and thin on k2_steam_aspyr.
- k2_steam_aspyr resolves only 16/33 sites with every event.* handler refused_ambiguous, so the state oracle (OnModuleLoad/OnAreaEnter) has no coverage there; k2_steam_linux lacks console/module.load_start; harness coverage will be K1-first by necessity.
- Detour install/uninstall are unsafe while a thread is in the prologue; Runtime::stop() is never invoked and DllMain detach leaves patches in place, so the harness cannot hot-swap hooks or cleanly unload; every hook-site change is a process restart.
- Hot reload and timers both hang off MainLoop; if the server loop pauses (menu, movie, pause, load) the command channel and timers stall, and the driver may misclassify that as a softlock.
- kMaxDepth=8 frames and thread_local ThreadFrames: a harness that calls originals of other hooked sites from inside a body nests fault frames; deeper nesting is unarmed and any fault there passes through to the game.
- Log I/O is fopen/fclose per line under a spin lock (runtime.cpp:212-218); a chatty per-tick harness logger under Wine will cost a file open per line on the server thread.
- The machine is low on memory; Xvfb+Wine+llvmpipe boots already take 30 s to 10 min (measure_boot.sh:1-15), so harness timeouts must be generous and runs serialized (lock.sh per display).
