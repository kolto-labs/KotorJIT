Ideation: KotorPhasor

Date: 2026-08-31 Topic: kotorphasor Focus: open-ended (whole codebase) Mode: repo-grounded

Codebase Context

KotorPhasor is a LuaJIT host DLL-injected into the KOTOR (Knights of the Old Republic) game engine via a binkw32.dll proxy trick and x86 inline detours, exposing ~769-772 engine routines plus a custom kp.* host API to embedded Lua scripts through an EventHandler surface. Targets KOTOR 1 Steam/Windows primarily; KOTOR 2 native Linux support is in progress. v0.1.0 just shipped out of a previously-private repository. An open PR just landed fixing an object-id corruption bug, a hook-install race, a new self-contained multiplayer avatar-sync example (raw UDP via LuaJIT FFI, no external dependencies), and a batch of memory-safety bugs (heap overflows, integer overflows, undefined behavior) found by two independent rounds of code review — not by any test suite.

The C++ core is organized by concern (src/api, src/events, src/hooks, src/image, src/lua, src/runtime, src/proxy, src/platform), with a heavily data-driven surface: routine, struct, and event tables are generated from data/*.toml via tools/gen_*.py. No docs/solutions/ or docs/CONCEPTS.md learnings corpus exists yet. No STRATEGY.md/PRODUCT.md exists.

External research found the closest prior art is K1SE (a narrower, SKSE-style function-extension mod for KOTOR 1) and NWNX (NWN's plugin-per-capability extender). There is real, current (2026) community demand for KOTOR multiplayer — validating the direction of the new avatar-sync example. Deadlystream, not Nexus Mods, is the dominant KOTOR modding hub, and KotorPhasor has no presence there yet. KotorPhasor's per-script fault-isolation/quarantine system is a genuine, currently-unadvertised differentiator versus every named prior-art tool.

Per-routine fault isolation for the routine bridge — refuted on follow-up

Fault isolation and test coverage
Amended 2026-08-31, after this idea was picked as the top survivor and someone went to implement it. Reading src/runtime/fault_guard.cpp end to end shows the premise is a misreading of the poison-flag pattern, the same way idea 15 misread hostapi.toml. FaultFrame::note_fault() already does two things on every guarded fault, not one: it poisons the specific site, and it calls set_live(false), which takes all Lua scripting out of service runtime-wide until lua reload. The per-site flags exist so a reload doesn't re-arm a known-bad site; they were never a mechanism for letting other sites keep running while one is down — a fault anywhere already stops everything, by design, because a lua_State unwound mid-pcall by a longjmp is left inconsistent and cannot safely be trusted again. Five ideation frames converged on this because they read the same file and drew the same wrong inference, not because five independent lines of evidence confirmed it.

Description (as originally proposed, now corrected): The original card asked to apply the per-site poison pattern to the 769-routine call bridge so "one bad call quarantines only that routine." That specific mechanism does not exist even for the ten event sites it was modeled on — a fault at any guarded site already stops the whole runtime. Separately, docs/user/api-status.md:274's "stack imbalance" case is not a hardware fault at all: it is a silent argument/return-count mismatch against the engine's own native VM stack, which never trips FaultFrame and which VmBinding (src/api/routines.hpp) has no accessor to detect. Building per-routine isolation for it would require new native reverse-engineering to expose a stack-depth check, not a copy of the existing pattern.

Basis
direct src/runtime/fault_guard.cpp:411-433 (FaultFrame::note_fault()), which the original card's evidence gathering read but did not follow to its actual behavior.
Rationale
What survives from this idea: the doc line it was based on was itself imprecise. Fixed instead, in docs/user/api-status.md: a routine call that hard-faults is caught and takes all scripting down until reload (matching the real mechanism); a silent stack imbalance has no detection or recovery at all today and needs a restart. That is the honest, shippable version of what this card was reaching for.
Downsides
Real per-routine isolation, if wanted later, is a materially larger project than this card estimated: it needs either a way to detect a native VM stack imbalance without a hardware fault (new RE work against an undocumented internal counter), or a redesign of the fault-recovery contract to permit resuming a lua_State after a longjmp mid-pcall, which fault_guard.cpp explicitly documents as unsafe today.
15%confidence Highcomplexity

Fault-injection harness for FaultFrame/setjmp recovery

Fault isolation and test coverage
Built 2026-08-31. tools/kp_faulttest.cpp links the real, unmodified src/runtime/fault_guard.cpp, triggers a genuine SIGSEGV inside a real KP_HOOK_GUARD_BEGIN region, and passes 12/12 assertions: the fallback runs, that site's poison flag is set, set_live(false) fires runtime-wide (not per-routine — see idea 1's amendment), poison survives a simulated lua reload, an unrelated second site stays clean, and — the negative case flagged as most likely to regress silently — a fault with no FaultFrame armed is correctly left unclaimed and kills the process, verified via a real forked child and its exit signal. Build: g++ -m32 -std=c++20 -O0 -g -Isrc tools/kp_faulttest.cpp src/runtime/fault_guard.cpp -o build/kp_faulttest.

Description: src/runtime/fault_guard.cpp implements a real setjmp/longjmp per-site fault-recovery mechanism (FaultFrame) — but nothing in the repository ever triggers an actual hardware fault through it. A repo-wide search for any test referencing FaultFrame, fault_guard, or setjmp outside the implementation file itself returns nothing. Script-level Lua error quarantine has a real test (scripts/harness/gameplay_tests/test_quarantine.sh); the native recovery path underneath it does not. The three most recent memory-safety bugs (heap overflow, two undefined-behavior integer casts) were all found by human code review, not by any test. Build a harness that deliberately forces a real fault — a bad pointer dereference, a corrupted stack — inside a hook body, and asserts the poison flag fires correctly and the process survives.

Basis
direct Verified via repo-wide search: zero tests reference FaultFrame/fault_guard/setjmp. Verified: test_quarantine.sh exists and tests only Lua-level errors, confirming the claimed gap is real and precisely as described. Independently proposed by five separate ideation frames.
Rationale
The project's advertised (if currently unadvertised in its own marketing) safety pitch versus SKSE/K1SE/NWNX is per-script crash containment — but the mechanism backing that pitch has never once been exercised by an actual crash in CI. Pairs naturally with Idea 1: this harness is the natural way to prove the per-routine isolation actually works once it's built.
Downsides
Deliberately forcing hardware faults (bad pointer derefs, stack corruption) inside a live process is inherently fragile test infrastructure to build and keep passing across platforms; likely needs its own dedicated CI lane rather than folding into the existing native test binaries.
85%confidence Highcomplexity

CI-built prebuilt release binaries

Modding-community distribution and docs

Description: Building KotorPhasor from source today requires a 32-bit mingw cross-compiler toolchain (mingw32-gcc-c++, i686-w64-mingw32-*) and a from-source LuaJIT build — a real barrier for an audience of KOTOR modders, not C++ developers. No GitHub Actions release workflow exists, and no prebuilt binary is attached to any release. The exact build recipe is already fully documented in docs/user/install.md; wire it into CI and publish kphasor.dll + the proxy binkw32.dll as release artifacts on every tag, so installing becomes "download and drop in the game folder."

Basis
direct Verified: docs/user/install.md requires the mingw32 toolchain; no .github/workflows release/artifact step exists in this repo. external Deadlystream is confirmed the dominant KOTOR modding hub by community consensus, and that audience installs prebuilt files, not source. Independently proposed by five separate ideation frames.
Rationale
v0.1.0 just released out of a repo that was private for its entire development cycle, with zero presence on any KOTOR distribution channel. Requiring every prospective modder to stand up a cross-compile toolchain before they can even try the thing is a self-inflicted adoption cliff that has nothing to do with the product's actual value — and the highest value-to-effort item in this whole ideation set, since the recipe is already written.
Downsides
Shipping prebuilt binaries for a DLL-injection tool raises a trust/provenance question (should releases be signed?) that the project hasn't had to answer yet; low cost to defer, but worth deciding deliberately rather than by default.
90%confidence Lowcomplexity

Close the kp.* gap, prioritized by the flagship example

Engine routine & host API coverage
Partially built 2026-08-31: exactly the two the example needed, not the full ~40-50. kp.gamedir and kp.time are now bound in src/api/compat.cpp (registered from runtime.cpp's boot_scripts, which already had the game directory in Config) and verified with dual-platform syntax checks (native -m32 Linux and the i686-w64-mingw32-g++ cross-compiler) against the real header layout. The avatar-sync script's fallback comments were corrected to say so; the fallback code itself was kept, since the script also has to run against older builds. The other ~38-48 names in the Downside below are untouched — this was scoped deliberately narrow, to the dogfooding evidence, not treated as a green light to sweep the whole backlog.

Description: Roughly 40-50 kp.* host functions — including basics like kp.print, kp.log, kp.time, and the whole kp.timer.*/kp.str.* families — are declared in data/hostapi.toml but return nil at runtime ("Spec only") today. The project's own new multiplayer example script had to hand-write fallback code around exactly this: its comments explain, verbatim, that kp.gamedir and kp.time are "spec-only (nil) on this build." Reprioritize the unbound-function backlog by what the project's own reference example actually needed, not by declaration order in the TOML.

Basis
direct Verified: scripts/examples/multiplayer/10_avatar_sync.lua lines ~303 and ~503-511 contain explicit hand-written fallback comments for exactly these two unbound functions. Independently proposed by four separate ideation frames.
Rationale
This is a dogfooding signal, not a hypothetical gap — the project's own showcase script needed workarounds for basics like time and directory access. If the flagship example needs defensive fallbacks for primitives that basic, every third-party scripter hits the same wall on day one.
Downsides
Some of the ~40-50 unbound names likely have real implementation cost hidden behind a simple-looking TOML declaration (memory-safety-sensitive ones especially); "prioritize by what the example needed" should not be read as "the rest are trivial."
85%confidence Mediumcomplexity

Stand up a learnings corpus, seeded from a bug that recurred

Modding-community distribution and docs

Description: Neither docs/CONCEPTS.md nor a docs/solutions/ directory exists anywhere in this repository — there is currently no durable place institutional knowledge survives a single session. The strongest evidence for why that matters, found during verification: the exact same bug — a missing !isfinite guard before a relational comparison that gates an unsafe numeric cast — was fixed in src/lua/value.cpp, and then, in a later commit the same day, found still present in src/api/routines.cpp's parallel object-id validation path. The second fix's own inline comment says "Same fix as lua/value.cpp's Object case for the same bridge." Nothing recorded the pattern after the first fix, so it had to be rediscovered. Create the corpus and seed it with this exact bug class as the first entry.

Basis
direct Verified via git blame: the guard in src/lua/value.cpp:96/113/115 landed in commit b28c129 (2026-08-30 20:48); the parallel guard in src/api/routines.cpp:134 landed over an hour later in de76e9b (21:55), citing the first fix by name. Confirmed no learnings corpus exists anywhere in the repo. The same gap showed up on three separate passes over the tree.
Rationale
A second pass called this the strongest direct-evidence claim of the fifteen candidates. It is near-zero cost (create two files, write one entry) against a documented, same-day recurrence of the identical bug class — the cheapest, highest-leverage item in this entire set.
Downsides
A learnings corpus only compounds if it's actually maintained going forward; standing it up is the easy part, keeping entries current as the codebase changes is the real, ongoing cost.

Reuse the K2 Linux adjudication pipeline for K2 Windows GOG

KOTOR 2 / Linux platform support
Unblocked and built, 2026-08-31. The binary turned out to exist on this machine after all, under a separate ongoing decompilation project. The real bug wasn't a missing adjudication methodology — gen_address_tables.py's k2_gog_aspyr entry was simply never given a reference_image path, so the generator had nothing to read. Fixing that one line and re-running the real generator resolved 32/33 sites at confidence 1.0 (this build is 95% natively symbol-named, so the heuristic adjudication pipeline this card described wasn't even needed) — installable: true, verified end to end with kp_imagetool identify against the real binary. Four more Windows builds (k1_amazongames, k2_win_cd_10, k2_win_cd_10b, k2_steam_aspyr) were registered the same way but are NOT installable yet: they're 47-61% named, so they genuinely do need the heuristic adjudication methodology this card originally proposed — that work is still open.

Description: K2 Linux (the Aspyr build) has 55 formally adjudicated VM bindings, produced by a documented accept/reject/insufficient-evidence method in data/adjudication/. K2 Windows GOG has zero bindings today — but the data file for it already carries the note "Binary not on this machine; table emitted to prove the generator generalises." The hard part of K2 support was never writing more hooks; it was building an adjudication methodology that proves a binding correct without full disassembly coverage. That methodology is proven once and explicitly built to generalize. Point it at the K2 Windows GOG binary next instead of starting the whole investigation from scratch.

Basis
direct Verified verbatim: data/addresses/k2_gog_aspyr.json contains "Binary not on this machine; table emitted to prove the generator generalises," with adjudicated_bindings: 0. data/adjudication/k2_linux_vm_bindings.json confirms 55 accepted bindings via the same pipeline. Independently proposed by four separate ideation frames.
Rationale
This reframes "add K2 Windows support" from a from-scratch reverse-engineering effort into "apply an existing, validated pipeline to a new binary" — a materially different cost estimate for the roadmap, and the thinnest-covered axis in this ideation run otherwise.
Downsides
Still gated on physically obtaining the GOG binary; the pipeline reduces the adjudication cost, not the acquisition cost, and some fraction of bindings may still need the same heuristic (non-disassembly) resolution K2 Linux needed for 8 of its 55.
80%confidence Mediumcomplexity

Live-engine verification for the GFF ghost-template

Multiplayer networking
Checked 2026-08-31, blocked: no speculative work done. Re-confirmed there is no KOTOR install anywhere in this environment: tmp/k1_harness (the directory scripts/harness/live_session.sh boots against) does not exist, and no swkotor.exe is present anywhere in the tree. A test that cannot run here was not written and reported as passing — that would be the same failure this whole idea exists to close. Unblocks as soon as a real game install is available to the harness.

Description: The new multiplayer avatar-sync example generates a GFF/UTC "ghost" creature template by hand, entirely in Lua. Its own header comment is explicit about the gap: verified only for internal byte consistency via a standalone Lua interpreter, "never loaded by the real engine, since there is no live KOTOR process in the environment this was written in." The project already has a working live-session test harness (scripts/harness/live_session.sh, recently centralized) capable of booting a real headless KOTOR session and driving it programmatically. Extend that harness to load the generated ghost template and assert it resolves to a valid, non-crashing object — closing the one verification gap the flagship new feature currently ships with.

Basis
direct Verified verbatim: scripts/examples/multiplayer/10_avatar_sync.lua states "never loaded by the real engine, since there is no live KOTOR process in the environment this was written in." Confirmed the live-session harness exists and is a real, reusable primitive.
Rationale
This PR is landing a brand-new multiplayer example built on an explicitly unverified code path. A broken ghost template is the very first thing a second player hits — converting "hope it works" into "proven it works" matters more here than on any other axis, and the reusable harness makes this cheap relative to the risk it closes.
Downsides
Requires an actual licensed copy of KOTOR available in the CI/test environment to boot against, which may not be feasible in every CI context this project runs in; may need to stay a local/manual verification step rather than a CI gate.
75%confidence Mediumcomplexity
