# fill:Menu-free boot: the engine's o

Mapped the K1 (GOG swkotor.exe) menu-free load/save machinery from the kotor_readable corpus (all functions advisory-ghidra, not byte-verified). The whole Load-Game handshake is GUI-free after CSWGuiSaveLoad::LoadGame 0x6cb0e0 issues its calls: the eight calls in the main-menu branch (UnpackGame, CreateServer, pause timers, StartConnectToSession, RequestStatus, SetPlayerCharacterName("test"), SetLoadFromSaveGame, SetLoadingSaveGame, SendLoadGameRequest) are synchronous in one client tick and only enqueue loopback frames; the server consumes them over subsequent server ticks. RunModule is NOT triggered by ModuleLoaded: server LoadModuleFinish sets server_mode=1 and broadcasts ServerStatus minor 1, the client's HandleServerToPlayerServerStatus answers automatically with the sys-admin text message "sModule.Run", and HandleServerAdminToServerMessage calls RunModule (server_mode 1->2), which for a save game itself loads the primary player (LoadPrimaryPlayer -> LoadCharacterFinish -> Login_Confirm + Module_Info), after which the client loads the module and sends ModuleLoaded (server case 2 needs server_mode==2 and player logged in) -> InitiateModuleForPlayer. The local loopback player is both player and sys-admin because StartConnectToSession passes flag byte 0x10. "test" resolves to TEMP:test.bic; if the file is missing LoginLocalCharacter returns 0 silently (no message, no NeedCharacter); NeedCharacter is only produced on the IFO-login path (LOGIN minor 0xf, used after EndStartNewModule(1) in the LoadPCAutoSave/module-warp path). Save-from-code: DoSinglePlayerAutoSave just sets auto_save_pending; MainLoop consumes it only when server_mode==2, stats idle, PC has an area and client area_not_ready_to_display==0; SaveGame arms the reentrant stats (phase 2) and the next server tick runs StallEventSaveGame end-to-end in one call, writing PARTYTABLE, GLOBALVARS, savenfo.res and then SAVEGAME.sav, then sets stats.field_14=1; the client-side StallServerCode clears continue_message_processing on its next tick. K2 GOG addresses for every function exist in MANIFEST/db; the K2 Linux ELF has identity rows only for RunModule, MainLoop, UpdateAutoSaveTimer, StartConnectToSession, AutoSaveOnEnteringModule, ReplyDialog; LoadGame/SaveGame/StallEventSaveGame/UnpackGame/handlers are only 'review'/'unresolved' matches from kx/match.py run v1.

## Implications
- Menu-free load = replay the main-menu branch of LoadGame from the client MainLoop detour in ONE tick: UnpackGame(save_number, name) [needs a CSWGuiSaveLoad* `this` only to forward to CopyGameToFutureGame; or call UnpackQuickSaveGame 0x6323a0 which is __stdcall and takes no `this`], CAppManager::CreateServer (only if AppManager->server==NULL; else DestroyServer+UnloadModule first as lines 863-866 do), PauseWorldTimer on both timers, StartConnectToSession(net,0,clientName,"",10,0x10) (must see CNetLayer+0x20060==0 first), RequestStatus, SetLoadFromSaveGame(1), SetLoadingSaveGame(1), SendLoadGameRequest(save_number,name,lastmodule). SetPlayerCharacterName("test") and DisableInput are optional for saves. Do not call 0x6cb0e0 directly unless a real CSWGuiSaveLoad panel with field_64 bit1 set and a valid manager is synthesized.
- No cave is needed for RunModule: after LoadModuleFinish the engine itself emits ServerStatus minor 1, the client auto-sends "sModule.Run", and RunModule runs because the loopback player is sys-admin (flag 0x10). A harness may still send "sModule.Run" (text to 0xfffffffd) or Module minor 7 as a forced retry, but only while server_mode==1.
- Boot-complete predicate (poll from the control plane, no pixels): server_mode(+0x10008)==2 && loading_module(+0x100b4)==0 && stats.continue_message_processing==0 && stats.load_game_error==0 && client loggedIn==1 && client area_not_ready_to_display(+0x288)==0 && server MainLoop counter advancing. Failure predicates: stats.load_game_error!=0 (DealWithLoadGameError), UnpackGame returned 0 (CORRUPT marker written), server_mode stuck at 1 for N ticks (RunModule never fired), loggedIn==0 after Module_Info (Module load discarded).
- Save-complete predicate for kotor.DoSinglePlayerAutoSave: (1) auto_save_pending(+0x100b8) returns to 0 (also happens when the save is refused: disk space or server_mode!=2, so it is NOT sufficient), (2) stats.phase(+4) observed ==2 then stats.field_14==1 / continue_message_processing back to 0 (cleared by client StallServerCode the next client tick), (3) file check on '<SAVES>/000001 - AUTOSAVE/SAVEGAME.sav' mtime >= request time (savenfo.res is written earlier than SAVEGAME.sav; using savenfo alone races). Autosave is only attempted when the PC is in an area and area_not_ready_to_display==0, so issue it after boot-complete.
- Checkpoint slots other than autosave can be created without GUI by sending Module minor 4 (SendPlayerToServerModule_SaveGame equivalent: slot DWORD, name, savegamename) or calling CServerExoApp::SaveGame(server, slot, &name, player) directly from the server MainLoop detour; StallEventSaveGame then runs in the next server tick regardless of GUI.
- Because the load runs as a multi-tick stall machine and StallEventSaveGame is one long tick, the driver must poll across ticks; commands that need server_mode==2 must be rejected while stats.continue_message_processing!=0.
- A menu-free NEW game (not from a save) has an engine path too: OnModulePicked's sequence with text "sModule.Load <module>" plus "test"; it depends on TEMP:test.bic existing for the login on status 3 (chargen writes TEMP:temp.bic, the test.bic writer is unlocated), or on the IFO login path (EndStartNewModule(1) -> LOGIN 0xf, which yields NeedCharacter if player+0x80==-1). Prefer booting from a shipped/committed autosave checkpoint.
- K2 GOG can reuse the same design with the listed addresses (entry layout differs: save_number at +0x1d4). K2 Linux ELF needs address recovery for LoadGame/SaveGame/StallEventSaveGame/UnpackGame/message handlers via kx/match.py verify pass or kotorphasor:adjudicated rows; RunModule, MainLoop, UpdateAutoSaveTimer, StartConnectToSession are already bound.
- Field/offset exposure for the state oracle: add stats.field_14 (+0x14) and stats.phase, server.auto_save_pending (+0x100b8), client.logged_in (global loggedIn), CNetLayer+0x20060 connect-in-flight, server.load_from_savegame (+0x100c4).

## Risks
- All read functions are advisory-ghidra (not byte-verified); offsets and control flow could differ from the shipped binary in details (e.g. Ghidra-merged branches in LoadGame).
- CopyGameToFutureGame (called by UnpackGame 006c.cpp:3208) has no definition in the readable tree; if it depends on CSWGuiSaveLoad state, a synthetic `this` may crash. UnpackQuickSaveGame 0x6323a0 (__stdcall, no this) is the safer entry.
- TEMP:test.bic absence is silently ignored (return 0) so a save load still works, but a stale TEMP:test.bic from a prior chargen would trigger an extra LOGIN/CharacterQuery exchange; TEMP: is cleaned by PopulateGames only when the GUI runs.
- HandleServerAdminToServerMessage relies on net_layer->GetPlayerInfo()->is_sys_admin; if a harness connects with a flag byte other than 0x10, sModule.Run is dropped and server_mode sticks at 1.
- StallEventSaveGame calls UpdateScreen/Draw/fade repeatedly; under Xvfb these are fine, but it is a single long tick that can look like a hang to a naive watchdog.
- auto_save_pending is cleared even when the save is refused (disk space < ~25.6MB or server_mode!=2), so 'pending cleared' is not 'save written'.
- The match-table K2 Linux candidates have margin 0.0 for several wrappers (identical bodies), so those addresses must not be used; only *Internal bodies with verify status are trustworthy.
- Client-side stats clearing (StallServerCode) runs on the client tick; if the harness executes only in the server MainLoop detour, the stats flip may lag one client frame.
