# k2-and-builds

Exactly one K2 game binary exists on this machine: the Aspyr native Linux ELF at "/run/media/brunner56/MyBook/SteamLibrary/steamapps/common/Knights of the Old Republic II/kotor2" (ELF32 i386 EXEC, stripped, sha256 ed043d21…), which is byte-identical to the corpus image TSL__k2_linux_swkotor2.elf and to the runtime's k2_steam_linux record; there is no swkotor2.exe anywhere in the Steam library, Downloads, GOG or Games dirs, but the corpus raw tree holds both Aspyr Windows PEs (steam 6a522e71…, gog 777bee23…) whose hashes match builds.inc, plus two CD 1.0/1.0b PEs. The K2 install's steamassets/ is a complete Windows data tree (chitin.key, modules/, swkotor2.ini, binkw32.dll, steam_api.dll) so a Wine run only needs the corpus exe dropped in. Per data/addresses, k2_steam_linux resolves 30/33 sites with all 11 required (console.do_console was demoted to optional for TSL, so no lua exec/OnConsoleCommand there), k2_gog_aspyr resolves 32/33 from real symbols with console working, and k2_steam_aspyr resolves only 16/33 with all event.* sites refused as ambiguous; both CD builds resolve 0/33. The Linux runtime is libkphasor.so injected via LD_PRELOAD with a __attribute__((constructor)) entry; there is no installer or doc for it, it has never been run against this install (no kotorphasor.log anywhere), and the ELF needs 32-bit libGLU.so.1 which is absent from /usr/lib but present in the Steam Linux Runtime. A latent bug matters for any K2 harness: api::select_game() has zero callers, g_game defaults to K1, so a K2 process would use the K1 routine table and defaults. K2-specific facts recovered: 877 routines (ids 0-876, 72 enum-only names), events/payload/struct research all K1-only, ini and saves under $XDG_DATA_HOME/aspyr-media/KOTOR2/ on Linux, start module 001EBO (swplayer.ini NewCharStartLevel), K2 modules ship as .mod+.rim+_s.rim+_dlg.erf. kpdiscover finds both games by content and returns the steamassets/ dir for K2 (chitin.key lives there), so the ELF must be found via root.parent as gen_address_tables._game_file already does.

## Implications
- Two live K2 targets are realistic today, and they have complementary gaps: (a) native kotor2 ELF via LD_PRELOAD=libkphasor.so under Xvfb (no Wine) with 30/33 sites but NO cheat console (no lua exec, no OnConsoleCommand); (b) k2_gog_aspyr under Wine using corpus TSL__k2_win_gog_aspyr_swkotor2.exe dropped as swkotor2.exe into a copy of steamassets/ (32/33 sites, symbol-sourced, console works, no SteamAPI dependency). k2_steam_aspyr is a weak third option (16/33, all event.* refused, every site low_confidence). Treat the CD builds as identification-only.
- The control plane must not depend on the cheat console: the console is absent on k2_steam_linux and, on every build, a console-driven harness needs pixel polling and XTEST typing. Since luaL_openlibs exposes ffi and OnTick fires on app.server_main_loop (resolved on all three K2 builds), an in-process channel (UDP/TCP or file queue serviced from OnTick, or a C++ command socket in the runtime) works identically on K1 Windows, K2 Windows, and K2 Linux.
- Fix api::select_game before any K2 harness work: nothing calls it, so a K2 process uses the K1 routine table (K1 ids/defaults). The harness should assert OnScriptLoad's game/build arguments AND probe a K2-only routine id (e.g. id 805+ or a K2-only name like ShowDemoScreen/GetScriptStringParameter) to catch table mismatch, and treat that as a required self-test.
- The harness must parameterise per build: image base (0x08048000 ELF vs 0x00400000 PE), config/save locations (K1: <game>/swkotor.ini and <game>/Saves; K2 Windows: steamassets/swkotor2.ini; K2 Linux: $XDG_DATA_HOME/aspyr-media/KOTOR2/{swkotor2.ini,saves,logs}), runtime game_dir (ELF: install root, next to kotor2; Windows: dir of the exe = steamassets/), start module (K1 end_m01aa vs K2 001EBO), module packaging (.mod+.rim+_s.rim+_dlg.erf on K2), and routine id space (772 vs 877).
- For a native Linux run: set XDG_DATA_HOME to a scratch dir so the ini/saves land in the harness tree; write EnableCheats=1 there only if a K2 console path is ever bound; provide 32-bit libGLU.so.1 (SteamLinuxRuntime path or install mesa-libGLU.i686) via LD_LIBRARY_PATH; RPATH='.' already covers the bundled libs; expect SteamAPI_Init to run against libsteam_api.so with no client (needs a probe run; steam_appid.txt=208580 may be needed as with K1).
- Event semantics and payload layout (CScriptEvent offsets, outer event ids 0x18/0x1A) and all kotor.struct offsets are K1-only research; on K2 the harness should exercise events only through fields that do not depend on that layout (script_name/object_id from vm.run_script) until K2 payload decoding is verified, and should never rely on kp.struct on K2.
- Discovery: use tools/kpdiscover.py --k1/--k2 (or KOTOR1_DIR/KOTOR2_DIR, or kotorphasor.toml [paths]) and never hardcode paths; for K2 the returned dir is the data tree (steamassets/), so derive the ELF as parent/kotor2 the way gen_address_tables._game_file does, and treat the returned dir itself as the Wine game dir.
- The runtime refuses unknown hashes and mismatched .text digests, so harness staging must copy binaries unmodified (no patched exes) and, for K1 Steam, use the deciphered image as the existing harness does; for k2_steam_aspyr the JSON lacks known_text/sentinel while builds.inc has a digest, so verify that path actually loads before relying on it.
- Stage from pristine sources: the K1 Steam install root is currently carrying a krayt.dll proxy and an appended swkotor.ini, so the harness should build its writable copy from a verified-hash exe plus data dirs rather than blindly copying the install root.

## Risks
- api::select_game has no callers: every K2 run today silently binds the K1 routine table, so any K2 'routine bridge works' claim in CHANGELOG/CONTRIBUTING is unverified at best and the ids can call the wrong engine command.
- No K2 Linux run has ever happened on this machine (no kotorphasor.log, LastPlayed=0, no aspyr-media dir); the LD_PRELOAD path, the SteamAPI gate, and the missing 32-bit libGLU are all untested here.
- k2_steam_linux has no console cave, so existing console-driven harness scripts (live_session.sh, drive_k1_console.sh, coverage 'cover ...' commands) cannot be ported as-is.
- k2_steam_aspyr is marked installable but has 15 refused_ambiguous sites (all EventHandlers) and every resolved site low_confidence; a wrong detour address on a hooked site corrupts the game silently. builds.inc's note still says not installable, so documentation and data disagree.
- K2 event payload decoding, outer event ids, and all struct offsets are K1-derived; on K2 they may read wrong offsets without faulting.
- The corpus Steam Aspyr K2 exe contains SteamAPI_Init and steamassets ships steam_api.dll; running it under Wine without a Steam client may refuse or crash, and no steam_appid.txt exists for K2.
- Ghidra coverage of the Linux ELF is poor (binary_id 18: 14743 funcs, 1826 named; nine accepted sites have no func row), so any additional K2 Linux caves (menu-free boot, reply pick, movie skip) need fresh adjudication rather than symbol lookup.
- The 'vanilla' K1 install root has been modified by a third-party proxy (krayt.dll) and repeated ini edits; harness copies made from it inherit that state.
- Memory pressure on this machine plus 3-7 GB game copies per harness tree (tmp/k1_harness, tmp/k2_harness, /dev/shm copies noted in harness_paths.sh) can exhaust /tmp and RAM; Xvfb lock-file failures were already hit.
