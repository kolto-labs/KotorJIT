# harness-history

The only boot pipeline that works today is K1-only: Xvfb :N 1024x768x24 + wine-11.0-staging win64 prefix at tmp/wineprefix-k1, LIBGL_ALWAYS_SOFTWARE=1, desktop-session env stripped, swkotor.ini forced to EnableCheats=1 and Frame Buffer=0 (the latter is what un-blacks the 3D world under llvmpipe), then a heuristic window scan (>=640x480, name not *Movie*, >64 unique colours) that reaches the main menu in 13-92s and a save via three XTEST clicks at fixed window fractions. Gameplay is detected by a deployed Lua probe (00_probe.lua) printing stock heartbeat scripts to kotorphasor.log, then a pixel discriminator at (40,46)==#292E36 tells menu/LOADING from HUD; the cheat console is then opened with grave and lines typed by xdotool at 60ms/char. Every failure class in the logs has a mechanical root cause: no probe deployed (5 runs of 3-10 min waiting for a line nothing would write), heartbeats firing under the LOADING splash, XSendEvent vs DirectInput, lost focus on the Dantooine save (10+ runs of 'console never accepted input', never root-caused), window-id churn producing empty geometry, /tmp tmpfs quota killing Xvfb, ffmpeg swallowing keystrokes, and block-buffered wine.log. The DoConsole detour (0x00401F00) is proven as a line injector: lua status/exec/reload work, engine routines called from the console mutate real state (AdjustAlignment, ExecuteScript, ApplyEffectToObject, AddPartyMember, warp), but it is one-way (return channel is only the log file), needs XTEST+focus, and has no oracle for warp completion beyond a 45s sleep. Layer 1 coverage scanner (kq-backed DLG/NCS graph) is the only part with clean, repeatable evidence (end_m01aa 16 dialogs/66 scripts/2 missing NCS in 38s; danm13 36/349/10). The reply-pick cave, render-off server tick, and campaign walker were deferred because NWScript has no ChooseReply, llvmpipe module loads are ~45s each, and the live 'cover' drive never ran (Xvfb failed on /tmp quota at the last attempt). Of the six live gameplay_tests none has a fully passing log; only the two kp_luatest tests pass; the [conscience], [meditation], [wounded] oracles were seen only via drive_k1_console/demo runs, and [arrival]/[alarm]/[ahto] were never observed in any small log. Saves: an Endar Spire AUTOSAVE, a Dantooine Game37 (danm13, party pmhc1/zaalbar/bastila), an unusable Game13 (no SAVEGAME.sav), and the '000000 - _pick' slot that pick_save.sh copies into so name-sort puts it first.

## Implications
- Reuse the proven substrate verbatim: Xvfb 1024x768x24, win64 prefix, LIBGL_ALWAYS_SOFTWARE=1, isolate_desktop_env, ini_headless (EnableCheats=1, Frame Buffer=0, Disable Movies=1, FullScreen=0). Nothing else about the boot is load-bearing; the window scan and click sequence are the parts to delete.
- Menu-free boot is the first cave to build: the current save-load path costs 3 XTEST clicks at fixed fractions, a window-id race, and is the single largest source of flake (focus, geometry, LOADING splash). Loading a save or StartNewModule from inside the process at app.server_main_loop (0x4BABB0) or module.load_start (0x4C8ED0, already resolved, no body) removes the entire pixel/xdotool dependency.
- Replace the console as command transport: DoConsole (0x00401F00) is proven only as a one-way XTEST line injector that needs focus and the HUD. An in-process command channel (file/pipe/socket polled from main_loop_body, executed on the server thread) gives the same `lua exec` semantics with a synchronous return value and zero X input.
- State oracle must come from engine calls, not logs or pixels: GetModuleName, GetIsConversationActive, GetPosition, GetIsDead, party enumeration, GetGlobalBoolean already work through kotor.* from Lua; the only thing the pixel discriminator ever told the harness (HUD present) is better expressed as 'module loaded AND not in a load screen', which should be exposed from the runtime (module.load_start + first OnTick after it).
- Softlock/hang detection has a natural probe: OnTick cadence (~4/s) from the server loop plus tick counter in `lua status`; a watchdog that sees ticks stop, or a module.load_start with no subsequent OnModuleLoad/OnAreaEnter within a budget, is a hang detector that needs no screen.
- Budget time per module load at 45-100s under llvmpipe and 13-92s to menu; any 'jump to arbitrary plot point' design must either use the render-off server tick cave (client_main_loop 0x602EB0 not detoured yet) or amortize via checkpoints (DoSinglePlayerAutoSave + OnSave/OnLoad sidecar) so each plot point is one load, not a chain of warps.
- Reply selection needs a cave: there is no NWScript ChooseReply; typing digits into a DirectInput console is exactly the keypress strategy the goal forbids. The conversation-manager write (deferred P2) is a prerequisite for walking dialogs blind.
- Every assertion must be on a deployed script's own print line or an engine query, and the probe (00_probe.lua) must be deployed by the driver itself; two of the existing assertions ([trace] present, k_def_attacked01 ran) pass without any input because of spawn traces and the Endar scripted fight.
- Environment preflight belongs in the driver: check /tmp free space, kill or avoid orphaned Xvfb on the chosen display (lock reclaim does not kill it), rm stale display-N.lock files, never use /dev/shm for game copies without cleanup, pkill -x swkotor.exe only, and keep per-run logs in fresh OUT dirs so evidence is not truncated.
- Screenshots stay as periodic sanity only: `import -window` + `magick %[hex:s.p{40,46}] %k` is cheap and already validated (menu 292E36/~22k colours, gameplay 004874/~69k), so keep it as an optional cross-check of the engine-reported state, never as the wait condition.
- K2 is unmapped by the harness: no script, ini tuning, window heuristic, or save exists for swkotor2.exe or the native kotor2 ELF; console.do_console may be unresolved on k2_steam_linux, which reinforces choosing an in-process channel that does not depend on the console site.

## Risks
- The Dantooine (Game37) 'console never accepted input' failure was never root-caused; if it is a focus/GUI-state issue it will also affect any design that still opens the console, and may indicate the game was in a GUI/conversation state on load (savenfo 'dantooine done?'), which an engine-state oracle must detect.
- Time-to-menu and module-load numbers vary 5x with host load (13s vs 92s to window; 10-minute wineboot stalls); fixed budgets from the harness (BOOT_WAIT 180-300, LOAD_WAIT 600, WARP_WAIT 45) are not safe timeouts for a watchdog.
- module.load_start is resolved in the address table but has no hook body; its calling convention and expected_bytes have not been exercised live, so using it for load-complete detection is unproven.
- The 15-hook build's EventHandler argument values are 'host-proven more than live-asserted' (PLAN-M1), so relying on OnAreaEnter/OnModuleLoad payloads for state may surface wrong data.
- kq (cleanhouse) is an out-of-tree Rust binary; the coverage scanner and any dialog-graph-driven walker depend on it being built and on kpdiscover finding the Steam install.
- tmp/ evidence is inconsistent with docs: docs/showcase-demos/README.md marks 50_enclave_arrival as ship with oracle seen, but no small log contains '[arrival]'; treat prior 'OK' claims as unverified until reproduced.
- Multiple stale locks and an orphaned Xvfb :85 exist right now; a driver that reuses display numbers 85-93 will collide.
- /tmp is a 16G tmpfs at 52% with prior quota failures; Xvfb, wine, and ffmpeg all write there.
- Every existing live test and demo used the same tmp/k1_harness copy, whose Saves/ and kotorphasor/scripts/ are mutated by pick_save.sh and deploy scripts; concurrent sessions will silently overwrite each other's deployed scripts and _pick save.
