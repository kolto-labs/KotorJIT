# fill:The only Lua/timer/command hoo

Mapped the K1/K2 main-loop and command-channel topology from the corpus, the live harness image, and the KotorPhasor hook registry. WinMain (K1 GOG/Steam-unpacked, 0x4041f0) is a single-threaded PeekMessage/GetMessage/DispatchMessage loop that calls CClientExoApp::MainLoop unconditionally every idle iteration and CServerExoApp::MainLoop only when AppManager->server != NULL; no thread creation appears in WinMain, and DoConsole is reached from WM_CHAR via HandleWMCharMessage on that same thread. A second, previously unnoted caller of the server loop exists: UpdateScreen 0x401c10, which the client loop invokes during module-load phases 1/3, so app.server_main_loop also ticks re-entrantly during LOADING. CClientExoAppInternal::MainLoop (0x602eb0, 4721 bytes) has no main-menu or movie early-return; it runs ResMan/ProcessInput every frame and returns only the exit flag, but movie playback blocks it inside WaitForMovie's messagepump spin, so a client-loop detour does not tick while a Bink movie plays. The harness image tmp/k1_harness/swkotor.exe matches the address table's reference sha256 and the 16 bytes at 0x602EB0 equal expected_bytes; the prologue is byte-identical in shape to the already-detoured server loop (6 displaced bytes, no relative operands), so flipping the site to kind=detour is a data change plus a HookRequest, not a signature gap (app_signatures.toml is install discovery, not byte signatures). On k2_steam_linux the resolved app.client_main_loop 0x081A5D72 is the 5662-byte Internal loop, not the 22-byte CClientExoApp wrapper at 0x819f56c; both the client and server Internal loops on the ELF take `this` on the stack (GCC cdecl), which contradicts hooksites.toml's convention="thiscall" and the KP_THISCALL main_loop_body, so the existing detour body would mis-read `this` there. K2 mac/ELF WinMain has the same client-unconditional/server-guarded structure and the same UpdateScreen-style secondary server caller (FUN_0819bfaa).

## Implications
- The boot verb (create server / load save / start module) must be drained from a CClientExoAppInternal::MainLoop detour: it is the only per-frame engine site that runs on the main thread at the main menu, and it runs every idle WinMain iteration with no menu/loading early-return (clientexoappinternal.cpp:10373-11079).
- Flipping app.client_main_loop to kind=detour is a data change (hooksites.toml:283 + sites[].kind in each build JSON via tools/gen_address_tables.py) plus one HookRequest in runtime.cpp:377-379 and a `void* KP_THISCALL client_main_loop_body(void*)`; expected_bytes already exist and match the live image, so no new signature work is needed for K1.
- Do not rely on the client-loop detour to fire during movies: WaitForMovie (clientexoappinternal.cpp:4870-4882) spins inside the loop and only pumps WndProc. A movie-skip cave must either detour PlayMoviesInExoArrayList 0x602af0 (return before PlayMoviesAsync) or set the exit-style flag the spin checks (field143_0x254 -> CancelMovie) from a WndProc-reachable path; the harness-design.md `client.play_movies` site is the right choice.
- The server-tick channel is not fully dead outside gameplay: UpdateScreen 0x401c10 (called at clientexoappinternal.cpp:10579 during load phases 1/3) runs CServerExoApp::MainLoop re-entrantly from inside the client loop. Hook bodies must tolerate main_loop_body running nested inside a client_main_loop_body frame (guard re-entrancy; do not assume one tick per WinMain iteration).
- Thread topology for K1 is settled: WinMain loop, messagepump, WndProc/DoConsole, client loop, server loop all run on one thread. A socket listener thread must only enqueue; execution happens in the client-loop drain. The same holds for the K2 ELF as far as the call graph shows (no thread-creating callees of WinMain).
- For k2_steam_linux the resolved site 0x081A5D72 is the correct Internal loop, but its convention is stack-`this` (GCC cdecl), so a K2-Linux body must be `void* __attribute__((cdecl)) body(void* self)` (like do_console_body at hook_bodies.cpp:517), and hooksites.toml's per-site convention must become per-build or per-platform. The existing KP_THISCALL main_loop_body would read garbage `this` on the ELF.
- Because the client loop's return value is the exit flag, a headless 'quit' verb can simply return 1 from the detour (WinMain ORs it into ExitProgram at _0040.cpp:2070) without touching WM_QUIT.
- Engine-native config channels exist at boot: dofile("startup.txt") runs after CClientExoApp::Initialize and before BeginIntro/DisplayMainMenu, and WinMain's FuncInterp(consoleInput) runs each frame when consoleCommandSubmitted is set. If FuncInterp/dofile accept engine commands, a startup.txt line could pre-configure the run (disable movies, cheats) with zero hooks; needs a read of FuncInterp.
- State-oracle fields named in harness-design.md (client.input_class, area_not_ready_to_display, stats.phase, continue_message_processing, load_game_error) are all read inside this loop (clientexoappinternal.cpp:10568-10593, 10894-10913), confirming they are the right per-frame phase discriminators to expose.

## Risks
- k2_steam_linux app.server_main_loop is marked detour/required with a thiscall body; if the runtime is ever loaded into the native kotor2 ELF as-is, `this` capture will be wrong and every server_tick receiver call will dereference garbage.
- Hooking the client loop adds a per-frame Lua/queue cost on the render thread; a slow drain (max_per_tick) or a blocking reply will stall rendering and WndProc, and under Xvfb+Wine may trip Wine's message-queue timeouts.
- Movies block the client-loop detour for their full duration (BeginIntro plays the logo movies before the main menu), so a boot verb issued too early waits until the intro finishes unless movies are disabled or PlayMoviesInExoArrayList is neutered.
- Re-entrant server ticks via UpdateScreen during LOADING mean the OnTick event and timers already fire in a partially-initialised state (area_not_ready_to_display forced to 1); harness watchdogs that count ticks as 'progress' will see ticks without gameplay advancing.
- The registry's `field` site kind referenced by harness-design.md is not implemented (registry.hpp:37-42) and src/hooks is uncommitted-modified; concurrent sessions may clobber it.
- Corpus decompilation is advisory-ghidra (not byte-verified); line-level claims about WaitForMovie spin counts (500) and field offsets (0x250/0x254/0x4bc) should be confirmed against the live image before caves depend on them.
