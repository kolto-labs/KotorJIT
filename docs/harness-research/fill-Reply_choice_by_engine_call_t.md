# fill:Reply choice by engine call: t

Read the K1 reply-pick chain end to end in the kotorxid readable corpus and cross-checked K2 (win gog aspyr, mac) plus the K2 Linux part database. The chain as posed is wrong in one link: CGuiInGame::HandleDialogReplyChosen 0x62e100 is not on the pick path; it is a server-to-client text echo called from inside CSWSDialog::HandleReply for other participants. The real path is CSWGuiDialog::SelectReply(visibleIdx) 0x6a7110 -> CGuiInGame::SetDialogSelection(idx,count,1) 0x62ada0 -> CGuiInGame::UpdateDialog 0x6339c0 (called synchronously by SelectReply and again every frame by CClientExoAppInternal::MainLoop 0x602eb0) -> CSWSObject::ReplyDialog(owner, clientId, GetReplyIndex(idx), idx==-3, dialog+0x64, fromClient=1) 0x4cb480 -> CSWSDialog::HandleReply 0x5a03c0. SelectReply takes a bare visible index and no CSWGuiControl*; it refuses idx >= count (returns 0) so it is safe to call blind. The presented replies live in two places that a state oracle can read without OCR: server side CSWSDialog+0x70 (current entry) with entries[cur].link_entries, and client side CGuiInGame+0x114 (count) / +0x118 (CExoString[] texts) / +0x11c (link index per visible row), copied into CSWGuiDialog+0x1970[0..19] by SetReplies 0x6a86a0 (which clamps to 20 rows). HandleReply's fromClient (param_6) gate only decides whether the chosen reply node's delay/wait_flags block runs (1 = skip it, exactly what the mouse path does; 0 = auto-advance path used by SendDialogReplies and HandleDialogSelection). HandleReply silently ignores a pick (returns 1) if a reply is already chosen (+0x74 != -1) or the expected entry index mismatches; it ENDS the conversation (returns 0 -> RunEndConversationScript) if linkIdx >= link_entry_count. K2 win gog has the same shape with different offsets (count +0x70, links +0x26e4, CGuiInGame sel at +0xe0..+0xec, HandleReply 0x757420 gating on +0x78/+0x74). K2 Linux 0x854ea9a is structurally consistent with ReplyDialog (149 bytes, 2 callees, constant 0x240) but the part db has zero identity/match rows, so it is still unverified by bytes.

## Implications
- Pick primitive (K1): dialog = *(CGuiInGame*+0x3c) where CGuiInGame = CClientExoApp::GetInGameGui(*(*(0x7A39FC)+4)) (0x5ed690); call the virtual at dialog->vtable+0x6c (CSWGuiDialog::SelectReply, base 0x6a7110 / cinematic 0x6a7e20) with (dialog, visibleIdx). It returns 1 if accepted, 0 if idx >= count, needs no control pointer, and drives the full server path synchronously. Use the vtable slot rather than the base address so the computer-panel variant is covered.
- Cheaper alternative with zero GUI coupling: CGuiInGame::SetDialogSelection(gui, idx, *(dialog+0x6c), 1) from the already-hooked app.client_main_loop detour; CClientExoAppInternal::MainLoop 0x602eb0 calls CGuiInGame::UpdateDialog once per frame (clientexoappinternal.cpp:10891) and consumes it. Do not call CSWSObject::ReplyDialog directly: it bypasses the client-side reply-table refresh and the +0xd0 pending flag.
- Thread constraint: all of SelectReply/UpdateDialog/HandleReply walk client and server object tables and run NWScript synchronously; they must execute on the game main thread (inside the MainLoop or DoConsole detours), never from the control-plane socket thread.
- Reply-list oracle without OCR (K1): count = *(CGuiInGame+0x114), texts = CExoString[count] at *(CGuiInGame+0x118) (8-byte {char* c_string, int length}, already TLK-parsed, without the '%d. ' prefix), link index per row = (*(CGuiInGame+0x11c))[i], current entry = *(dialog+0x64). Server truth: dlg = *(ownerCSWSObject+0x34); cur = *(dlg+0x70); active links = entries[cur].link_entries (0xb0 stride entries at dlg+0x8, count at entry+0xa8, ptr at entry+0xac, 0x18-stride links with index at +0x10). Optional detour for event-style capture: CGuiInGame::HandleDialogReplies 0x634340 (texts=param_4, links=param_5, active=param_19, inactive=param_20, entry=param_21, last=param_25) or server-side CSWSDialog::SendDialogReplyNode 0x5a1c00 (8 args).
- State predicate 'pick will be accepted' = *(CGuiInGame+0xb4)!=0 && *(CGuiInGame+0xd0)==0 && *(CGuiInGame+0x114)>0 && *(dlg+0x74)==-1 && *(dlg+0x70)==*(dialog+0x64) && *(owner+0x48)==0. If +0x74 != -1 the pick is silently dropped (HandleReply returns 1) -- poll for +0x74 == -1 rather than retrying blindly.
- Never send linkIdx >= link_entry_count to ReplyDialog/HandleReply: that returns 0 and ends the conversation (RunEndConversationScript, +0x214 delete). SelectReply's own idx<count check prevents this when going through the GUI layer.
- Skip/abort primitives: SetDialogSelection(-3, n, 1)+UpdateDialog aborts the conversation via HandleReply's abort branch; SetDialogSelection(-2, n, 0) routes to HandleDialogSelection -> CloseDialog (client side only). Entry-continue (skip NPC line) is the isReply=0 path with idx 0.
- Softlock detector for dialogs: dialog active (+0xb4) with +0x114==0 for > N seconds while owner+0x48==1 (waiting on IsDialogDelay / IsSoundPlayingInDialog) or dlg+0x60==1 waiting for sound that never ends; CSWSObject::UpdateDialog 0x4cd580 is the per-frame server gate.
- Reply cap: SetReplies clamps to 20 rows and only 20 link slots exist at dialog+0x1970; pick by server link index if a node ever has more than 20 links.
- Greyed (display_inactive) rows are in the client table and HandleReply does not re-check their Active script; the walker must not pick rows whose link entry failed CheckScript (recompute CheckScript server-side or read control enabled state) or it will exercise unreachable branches.

- Every function read is 'advisory-ghidra' (not byte-verified); K1 HandleDialogSelection's decompile has garbage args (unaff_retaddr) so its ReplyDialog argument order is inferred from K2.
- CSWGuiDialog+0x64 = entry index is inferred from K2 (explicit) and the HandleReply expectedEntry check; K1 decompile shows unaff_EDI.
- The K2 Linux 0x854ea9a identity has no recorded match/identity row in the corpus; only shape (size 149, consts 0x240, callee with 0x104/0x108/0x10c/0x110) supports it.
- Calling the chain off the main thread, or while CGuiInGame+0xd0 is still pending, will crash or drop the pick.
- fromClient=1 skips the reply node's delay/wait flags exactly like the mouse path; if a test needs the auto-advance timing (fromClient=0) it must use HandleDialogSelection semantics instead.
- K2 SelectReply calls Achievements::OnDialogOptionChosen (FUN_00401040 on win) which may touch the Steam/GOG overlay under Wine.
- The HandleDialogReplies 25-arg prototype in K1 is __thiscall with stack args; the exact meaning of params 6-18 and 22-24 (speaker/listener/camera arrays) was not fully mapped, only texts/links/counts/entry index.
